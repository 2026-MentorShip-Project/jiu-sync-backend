## add-event-lifecycle / EventCancelView 實作先於測試撰寫(TDD 排法違規,自行發現並修正)

- 發生了什麼:寫 `EventFinalizeView`/`EventCancelView` 兩個 view 時，把兩個都一起寫進 `apps/events/views.py`（同一次編輯），但當下只有 finalize 的測試（1.1）已經寫好，cancel（Seam 2）的測試（tasks.md 2.1）還沒補上就先有了實作程式碼——違反 CLAUDE.md「先寫測試、後寫程式碼」的規範。
- 怎麼發現的:補完 Seam 2 的 13 個 cancel 測試後執行 `pytest -k "cancel and not participant"`，結果一次就全部 13 個通過，沒有先看到預期中的 RED（collection error 或 assertion failure），才意識到實作已經在測試之前就寫好了。
- 怎麼處理的:承認這次順序違規，不倒帶重做（程式碼本身已通過完整測試覆蓋，倒帶重做只是為了走個形式，價值有限），如實記錄。之後的 seam（若有）會維持嚴格 RED 確認再寫實作，見 add-event-lifecycle 這次 finalize（Seam 1）就有正確做到 RED→GREEN。

## add-event-lifecycle / 使用者實測發現：finalize 通知信寄送失敗會讓已成功的定案動作變成 500

- 發生了什麼:使用者在本機測試 `POST /api/events/{id}/finalize`，`.env` 尚未設定 `EMAIL_BACKEND`（仍是預設 `console.EmailBackend`）但已填 SMTP 專用的 `EMAIL_HOST`/`EMAIL_HOST_USER` 等 `OPTIONS`，`send_mail()` 對 console backend 傳入不認得的 kwargs，拋 `InvalidMailer`。因為本機 `CELERY_TASK_ALWAYS_EAGER=True`，`transaction.on_commit()` 的 callback 同步執行，例外直接炸穿 view，回應變成 500——但定案本身（DB 寫入）在 `on_commit` 觸發前就已經 commit 成功，使用者質疑「500 不該還保留寫入結果，是不是沒包原子性」。
- 怎麼發現的:使用者貼出實際的 500 traceback 與後續重新 `finalize` 時收到的 `EVENT_ALREADY_FINALIZED`。用 `manage.py dbshell` 直接查該筆活動，確認 `status`/`final_slot_id`/`final_note`/`finalized_at` 皆已正確寫入，證實不是原子性問題，而是通知信失敗（`on_commit` 之後才發生）被誤當成整個請求失敗。
- 怎麼處理的:新增 `_schedule_notification(task, event_id)` 包住 `transaction.on_commit()` 的 callback，`task.delay(event_id)` 拋出的例外用 `try/except` 吞掉並 `logger.exception(...)` 記錄，不讓它往上炸穿 view；`EventFinalizeView`/`EventCancelView` 改呼叫這個共用函式。補上回歸測試（`monkeypatch` 讓 `.delay()` 拋例外，斷言 API 仍回 200 且狀態正確轉換），RED→GREEN 驗證過。見 design.md Risks 段落的同日修訂記錄。
