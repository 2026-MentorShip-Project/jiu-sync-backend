## add-participant-responses / Codex 二次審查抓到 token 消費的 TOCTOU 落差,design.md D9/D13 皆未涵蓋

- 發生了什麼:使用者貼上一份對此分支的 Codex 二次審查報告。核心發現:`PATCH .../responses/{responseId}` 開頭的早期檢查(token 是否過期)用請求一開始的 `now`,但真正保證一次性消費的 compare-and-swap `UPDATE ... WHERE used_at IS NULL`(前一則 incident 剛修好的併發保護)發生在共用前置條件檢查與 slot 驗證之後,中間有真實時間間隔——CAS 只檢查 `used_at IS NULL`,沒有重新核對 `expires_at`,token 若剛好在這段空檔到期仍會成功消費。次要發現(低嚴重度):`ParticipantResponseAccessToken` 無清除策略,資料表隨核對次數無限累積。
- 怎麼發現的:先讀程式碼確認 Codex 描述的兩個呼叫點(`views.py` 早期檢查、CAS 區塊)與其引用行號相符,判定為真實落差,不是誤報。用真實時間流逝(在 `_check_participation_preconditions` 呼叫點人為注入 0.3 秒延遲、token 效期設 0.1 秒)寫測試驗證:修正前 FAIL(token 仍被成功消費,回應 200)、修正後 PASS(401 `ACCESS_TOKEN_INVALID`)。
- 怎麼處理的:CAS 的 `UPDATE` 加上 `expires_at__gt=<CAS 當下重新取得的 now>` 條件,`claimed_at` 與 `used_at` 寫入值用同一個新變數,不沿用早期檢查的舊 `now`,補上述測試(見 design.md D13)。次要發現(token 累積)判定為非 blocker,記入 design.md Risks,不動程式碼。全套 `pytest`(155 passed)、`ruff check`、`manage.py check` 皆乾淨。
