## terraform-ec2-provision / task 4.2 — operator user 缺少 SSM control-plane 權限(與 instance profile 無關的另一組缺口)

- 發生了什麼:task 3.1 建好的是「instance 端」的 IAM role/instance profile(`AmazonSSMManagedInstanceCore`),讓 EC2 上的 SSM Agent 能對 SSM 服務認證;但驗證 4.2 需要 operator 端(`this-is-so-sweet-backemd` IAM User,即本機 `aws` CLI 使用的身份)呼叫 SSM control-plane API 來確認可用 Session Manager 管理 instance。實測 `aws ssm describe-instance-information` 與 `aws ssm send-command`(document `AWS-RunShellScript`)皆回傳 `AccessDenied`,分別缺少 `ssm:DescribeInstanceInformation`(resource `arn:aws:ssm:ap-northeast-3:376129879394:*`)與 `ssm:SendCommand`(resource `arn:aws:ec2:ap-northeast-3:376129879394:instance/i-0f6d5dc974e91bbf6`)。這是 operator User 身上全新的一組權限缺口,跟 3.1 那六輪(operator 對 IAM role/policy 本身的管理權限)性質不同,是 operator 對 SSM 服務的權限。`~/.aws/credentials` 只有一組 `[default]` profile,無其他更高權限 profile 可切換。
- 怎麼發現的:直接執行上述兩個指令的錯誤訊息;另以 `aws sts get-caller-identity` 確認目前 CLI 身份確實是 `this-is-so-sweet-backemd`,排除用錯 profile 的可能。
- 怎麼處理的:尚未解決,依規則不自行擴大授權範圍,停止並回報使用者需在 operator User 的 inline policy 補上至少 `ssm:DescribeInstanceInformation`、`ssm:SendCommand`、`ssm:GetCommandInvocation`(驗證 whoami 執行結果需要);若要用題目原本要求的真互動式 `aws ssm start-session` 則還需 `ssm:StartSession`(建議連 `ssm:TerminateSession`、`ssm:ResumeSession` 一併補上)。port 22 部分已獨立驗證完成(`nc -zv -w5 56.155.65.244 22` → `Operation timed out`,不依賴 AWS 權限)。task 4.2 未打勾,待補權限後重跑。

### 結案(下一輪)

使用者於既有 inline policy(`iam-setting`)追加 `ssm:DescribeInstanceInformation`、`ssm:SendCommand`、`ssm:GetCommandInvocation`、`ssm:StartSession`、`ssm:TerminateSession`、`ssm:ResumeSession` 後重試。先以 `aws iam simulate-principal-policy` 驗證 `ssm:SendCommand`、`ssm:DescribeInstanceInformation`、`ssm:StartSession` 三個關鍵 action 對 resource `*` 皆為 `allowed`,才繼續。首次執行 `aws ssm describe-instance-information` 仍短暫 `AccessDenied`;用 `aws iam get-user-policy` 直接讀出 inline policy 文件內容,確認 action/resource 定義本身完全正確(與拿到的 AccessDenied 動作、resource 一致),判定屬 IAM 變更傳播延遲(非新的權限缺口,未新增/猜測任何 action),等待約 20 秒後重試即成功——`PingStatus: Online`。接著以 `aws ssm send-command`(document `AWS-RunShellScript`,指令 `whoami`)+ 輪詢 `aws ssm get-command-invocation` 確認 `Status: Success`、`StandardOutputContent: "root\n"`,證明 operator 可透過 SSM control-plane 對 instance 執行指令,不依賴 SSH key pair。互動式 `aws ssm start-session` 因本機未安裝 `session-manager-plugin` 而略過(非必要驗證項,send-command 已足以證明)。重新執行 `nc -zv -w5 56.155.65.244 22` 再次確認 `Operation timed out`,port 22 仍未開放。task 4.2 已打勾。

## deploy-django-app / task 6.1 — deploy.sh 自身邏輯有兩個 bug(已自行修正)

- 發生了什麼:第一次真正執行 `./infra/scripts/deploy.sh`(`.env` 已由使用者建好)在「git clone」步驟就失敗:`fatal: destination path '/opt/jiu-sync-backend' already exists and is not an empty directory`——因為該目錄已因存放 `.env` 而存在且非空,原本的 `[ -d .git ]` 判斷只處理「目錄不存在」與「已是 git repo」兩種情況,漏了「目錄存在但還不是 git repo」這第三種情況。修正後重跑,又在同一步驟踩到第二個獨立 bug:`fatal: $HOME not set`——SSM `AWS-RunShellScript` 執行環境不是 login shell,即使指令以 root 身分執行,`$HOME` 仍未設定,導致 git 找不到使用者手動建好的 `~/.gitconfig`/`~/.git-credentials`(`credential.helper = store`)。
- 怎麼發現的:兩次都是直接看 `deploy.sh` 印出的 remote STDOUT/STDERR(SSM command invocation 內容);第二個問題另外用一支獨立診斷用 SSM 指令確認 `whoami` → `root` 但 `echo $HOME` → 空字串,且 `/root/.gitconfig`、`/root/.git-credentials` 確實存在且內容正確,排除是使用者手動設定 git 認證那步做錯。
- 怎麼處理的:兩個都判定為 `deploy.sh` 自身邏輯的 bug(非人工前置設定問題),已自行修正:(1) 目錄非空時改用 `git init` + `remote add` + `fetch` + `checkout -f -B <default-branch>` 就地初始化,不再對已存在目錄呼叫 `git clone`;(2) 在 remote script 最前面加上 `export HOME="$(getent passwd "$(whoami)" | cut -d: -f6)"`。`bash -n infra/scripts/deploy.sh` 語法檢查通過,兩次重跑皆證實各自的錯誤訊息消失、往下推進到下一步驟。
