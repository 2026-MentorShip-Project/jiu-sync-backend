# 2. 介面/使用者體驗設計(後端角度)

揪甘心有兩種使用者:

- **主揪**:用 Google 帳號登入,建立活動、管理投票結果、定案,並使用 AI 推薦餐廳。
- **參與者**:從主揪分享的連結進來,**不需要註冊或登入**就能投票、改票、留言。

前端在另一個 repo。本章從後端角度說明哪些 API 設計直接影響使用體驗,以及做了哪些考量。

## 2.1 統一、可程式化判斷的錯誤回應

**為什麼關鍵。** 同樣是 409,「活動已取消」、「投票已截止」、「已經定案過了」要對使用者顯示不同的說明與下一步。如果錯誤格式不一致,前端只能顯示籠統的「發生錯誤」。

**設計決策**

- 所有非 2xx 回應統一為 `{"message": "...", "code": "..."}`(`config/exceptions.py`)。`message` 是可以直接顯示的中文訊息,`code` 給前端做分支判斷,例如 `EVENT_ALREADY_CANCELLED`、`VOTING_CLOSED`、`AI_RECOMMENDATION_QUOTA_EXCEEDED`。
- 400 驗證錯誤另外附上 `errors: [{field, code, message}, ...]`,**一次列出所有出錯的欄位**,前端可以同時把所有錯誤欄位標紅,不用讓使用者一次修一個。
- 404/500 也走同一個格式(`handler404`、`handler500`),前端不會收到 Django 預設的 HTML 錯誤頁。

## 2.2 參與者免登入投票與改票

**為什麼關鍵。** 揪團成不成,取決於朋友願不願意點開連結填完。多一個註冊步驟,就會少一批人填。但完全不驗證身分,任何人都能改別人的票。

**設計決策**

- **首次投票只要暱稱 + 手機末三碼**(`POST /api/events/{id}/responses`)。同一活動內暱稱不可重複,末三碼以 Django 密碼雜湊儲存,不存明碼。每個候選時段可以選「可以 / 勉強可以 / 不行」三種狀態。
- **改票分兩步**:先 `POST .../responses/verify` 用暱稱 + 末三碼核對身分,成功後拿到一組 **30 分鐘內有效、只能用一次**的存取憑證,再帶著它 `PATCH .../responses/{responseId}`。換手機或清掉瀏覽器資料時,重新核對一次就能找回自己的投票。
- **不洩漏誰投過票。** 「暱稱不存在」和「末三碼錯誤」回同一個 401 訊息;暱稱不存在時仍對一個固定雜湊做一次比對,讓兩種失敗的回應時間也差不多。
- **送出後直接拿到最新彙整。** 投票與改票成功後回傳完整的活動資料(含各時段彙整),前端不用再打一次 `GET`。
- **前置條件依序檢查**:連結是否失效(410)→ 活動是否進行中(409 `EVENT_NOT_ACTIVE`)→ 是否已過截止時間(409 `VOTING_CLOSED`)。每種情況都有專屬的 code,前端能告訴使用者「為什麼不能投」以及「該找主揪重新開放」。

## 2.3 用輕量輪詢同步多人的變化

**為什麼關鍵。** 大家常常同時開著同一個活動頁。有人投票、主揪定案時,其他人的畫面要能跟上,否則會出現「我以為還能投」的狀況。

**設計決策**

- `GET /api/events/{id}/poll` 只回傳變化訊號:`status`、`displayStatus`、`eventUpdatedAt`、`responseCount`、`latestResponseAt`、`commentCount`、`latestCommentAt`,不含投票明細與留言內容。
- 前端每 10 秒呼叫一次,和上次的值比較,有變化才去拉完整資料。這支端點只需要 3 個查詢,遠比完整的活動詳情便宜。
- `latestResponseAt` 取的是 `updated_at` 的最大值,所以「有人改票」也偵測得到,不只是「有新投票」。

## 2.4 活動顯示狀態由後端算好

**為什麼關鍵。** 「投票中」、「已截止待定案」、「已定案、聚會還沒到」、「聚會已過」、「已取消」、「連結已失效」對應不同的畫面與可用按鈕。如果讓前端自己用時間判斷,時區或時鐘誤差就會導致畫面錯誤。

**設計決策**

- 後端以純函式 `compute_display_status()`(`apps/events/lifecycle.py`)算出 6 種 `displayStatus`,前端直接依值顯示。
- 「聚會日期是否已過」以台灣時間的當天判斷(曾經用 UTC 日期判斷,導致台灣時間 00:00–08:00 顯示錯誤,已修正)。
- 定案或取消超過 7 天,公開連結回 410 `LINK_EXPIRED`;但主揪對自己活動的管理動作(取消、重新開放)不受這個限制。

## 2.5 不怕主揪弄丟分享連結

**為什麼關鍵。** 主揪建立活動後,如果沒複製連結就關掉分頁,參與者就進不來了。

**設計決策**

- 建立活動成功後,非同步寄一封含分享連結的信到主揪的 Google 帳號信箱。
- 定案、取消、重新開放也會寄信通知留過 email 的參與者。每位收件人各收一封獨立的信,不會在收件人欄位看到其他人的 email。

## 2.6 留言板

**設計決策**

- 任何人都能留言(暱稱 40 字、內容 200 字以內),不需要先投票。活動已定案或取消後仍可留言,只有連結失效後不行。
- 列表用 cursor 分頁(`{comments, nextCursor}`),每頁 10 則、由新到舊。往回翻頁時,即使中間有人留新言,也不會重複或漏掉。
- 同一 IP 對同一活動 2 秒內只能留一則,超過回 429 `COMMENT_RATE_LIMITED`,防止連點洗版。
- 主揪可以刪除留言(軟刪除,保留紀錄)。

## 2.7 AI 餐廳推薦

**為什麼關鍵。** 這是產品的差異化功能,但每次呼叫上游都要付費,而且回應很慢(開發時實測延遲中位數約 24 秒)。

**設計決策**

- **偏好條件全部選填。** 後端會自動補上活動的地點、出席人數與定案時段,回應中的 `resolvedPreferences` 重述實際採用的條件,讓主揪確認 AI 理解的需求是否正確。
- **額度清楚透明。** 每位主揪每月 20 次(可設定),只有成功才計次,失敗或逾時不計。成功回應直接附上剩餘次數,另有 `GET /api/me/ai-recommendation-quota/` 可以查詢;服務未設定時,`serviceAvailable` 為 false,前端可以先把按鈕停用。
- **防止重複送出。** 同一活動已有進行中的請求時,回 409 `AI_RECOMMENDATION_IN_PROGRESS`,前端可以停用按鈕,避免使用者因為等太久而重複扣次。
- **錯誤分類明確。** 上游逾時回 504,上游失敗或找不到符合條件的餐廳回 502,並附上 AI 給的說明。
- **選定餐廳可以反悔。** `PUT .../selected-restaurant/` 可以換選,重送同一間不會改變任何紀錄;選定結果會出現在活動詳情的 `selectedRestaurant`。
