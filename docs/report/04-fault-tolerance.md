# 4. 容錯性設計

## 設計原則

揪甘心的容錯設計依照三個原則,重要性由高到低:

1. **資料不能錯。** 一個請求失敗時,不能留下寫了一半的資料;兩個請求同時改同一筆資料時,結果必須和「依序執行」一樣。例如:同一個活動不能同時被定案兩次,一次性憑證不能被用兩次,AI 額度不能被超用。
2. **附屬功能壞掉,不能拖垮主功能。** 寄信、留言限流、可觀測性都是附加的。它們故障時,投票、建立活動等核心 API 必須照常運作。
3. **錯誤不能被吞掉。** 可以選擇不讓使用者看到失敗,但一定要留下 log,事後查得到原因。

可用性排在這三項之後:整個後端跑在一台 EC2 上,機器本身故障時服務會中斷(見第 6 章)。

## 4.1 一覽:各種故障會發生什麼

| 故障情境 | 系統會怎麼反應 | 程式位置 |
| --- | --- | --- |
| 兩個人同時定案、取消或重新開放同一個活動 | 只有一個成功,另一個回 409 並說明原因 | `apps/events/views.py`(條件式 UPDATE) |
| 同一組改票憑證被同時送出兩次 | 只有一個成功,另一個回 401 | `ParticipantResponseDetailView.patch()` |
| 取消活動時寫到一半出錯 | 狀態轉換與軟刪除投票一起回滾 | `EventCancelView`(`transaction.atomic`) |
| 寄通知信失敗(SMTP 錯誤、Redis 連不上) | API 照常回成功,錯誤寫進 log | `_schedule_notification()` |
| Redis 掛掉或設定錯誤 | 留言限流自動失效(fail-open),留言照常寫入,記一筆 warning | `_try_acquire_comment_rate_limit_lock()` |
| Perplexity 逾時 | 回 504,推薦紀錄標成 failed,不計次 | `apps/recommendations/views.py` |
| Perplexity 回錯誤、格式不對、找不到餐廳 | 回 502,不計次,上游原文不寫進 log | 同上、`engines/perplexity.py` |
| AI 推薦成功但結果寫不進資料庫 | 紀錄改為 failed,不會一直佔著額度 | `RestaurantRecommendationView.post()` |
| 處理 AI 推薦的程序中途當掉 | pending 紀錄 5 分鐘後自動不再計入額度 | `apps/recommendations/quota.py` |
| Alloy 掛掉或 Grafana Cloud 連不上 | app 不受影響;Alloy 會自動重試,恢復後補送暫存的資料 | `docker-compose.prod.yml`(沒有服務依賴 alloy) |
| 任一 container 異常結束 | Docker 自動重啟(`restart: unless-stopped`) | `docker-compose.prod.yml` |
| 部署時 `.env` 缺少必要設定 | 在動到任何服務前就中止,正在跑的版本不受影響 | `infra/scripts/deploy.sh` |
| EC2 或根磁碟損毀 | **服務中斷,資料庫資料無法復原**(目前沒有備份) | 見第 6 章 |

## 4.2 外部服務故障

系統只依賴四個外部服務,都不在投票、留言這些核心流程上。

**Perplexity(AI 餐廳推薦)**

- 連線逾時 5 秒;整體期限預設 45 秒(`PERPLEXITY_TIMEOUT_SECONDS`)。以串流方式讀取回應,自己計算累計時間,避免上游一點一點慢慢回傳時無限延長。
- 每一種失敗都有明確的分類與對應的 HTTP 狀態:

  | 原因 | 回應 | 是否計次 |
  | --- | --- | --- |
  | 服務未設定(沒有 API key) | 503 `AI_RECOMMENDATION_UNAVAILABLE` | 否,而且不會建立紀錄 |
  | 上游逾時 | 504 `AI_RECOMMENDATION_UPSTREAM_TIMEOUT` | 否 |
  | 上游 HTTP 錯誤、連線失敗、回應格式不對 | 502 `AI_RECOMMENDATION_UPSTREAM_FAILED` | 否 |
  | 找不到符合條件的餐廳 | 502,附上 AI 給的說明 `notes` | 否 |

- **不自動重試。** 每次呼叫都要付費,而且重試會讓使用者等更久。失敗時由使用者決定要不要再試,失敗不扣次數。
- **這個功能壞掉,其他功能完全不受影響。** 它只在主揪主動點選時才會被呼叫。

**Google(主揪登入)**

- 使用 `google-auth` 驗證 id_token,需要向 Google 取得簽章憑證。驗證失敗一律回 401 `INVALID_ID_TOKEN`。
- 已經登入的主揪不受 Google 故障影響:access token 與 refresh token 都由本系統自己驗證,不需要再問 Google。
- 參與者完全不需要 Google。

**SMTP(通知信)**

- 寄信在 Celery worker 上執行,而且是在資料庫 commit 之後才排入佇列(`transaction.on_commit`)。所以不會出現「信寄出了,但資料其實沒存進去」的情況。
- 排入佇列失敗時(例如 Redis 連不上),只記 log,API 照常回成功。

**Grafana Cloud(可觀測性)**

- Alloy 把 metrics 的待送資料(WAL)與 log 的讀取進度存在 volume 裡,重啟後從上次的位置繼續,不重送也不遺漏。

## 4.3 逾時與重試

| 位置 | 逾時 | 重試 |
| --- | --- | --- |
| Perplexity 連線 / 整體 | 5 秒 / 45 秒 | 無(使用者自行重試,不扣次) |
| 留言限流的 Redis 連線與指令 | 各 1 秒 | 無(連不上就 fail-open) |
| Google 簽章憑證下載 | `google-auth` 預設 120 秒 | 無 |
| SMTP 寄信 | **未設定**(Django 預設為無逾時) | **無**(見 4.7) |
| gunicorn worker | `timeout=60` | — |
| 短 id 碰撞(活動、投票、留言) | — | 最多 3 次,每次在獨立的 savepoint 內重試 |
| 部署腳本等待 SSM 完成 | 900 秒 | 輪詢最多 200 次 |

**為什麼大部分都不自動重試?** 多數寫入操作不是冪等的。例如「建立活動」重試一次,可能就多出一個活動。所以只在「確定重試不會造成重複副作用」的地方重試(短 id 碰撞:前一次根本沒寫入)。

**gunicorn `timeout` 的限制:** 在 `gthread` 模式下,`timeout` 只檢查 worker 程序是否還活著,不會中斷跑太久的單一請求。單一 AI 請求的時間上限,實際上由引擎的整體期限控制。

## 4.4 錯誤處理策略

**統一格式。** 所有錯誤都經過 `config/exceptions.py`,回應統一為 `{"message", "code"}`,400 另附 `errors` 陣列(見第 2 章)。

| 狀態碼 | 代表什麼 |
| --- | --- |
| 400 | 輸入驗證失敗,`errors` 列出每個欄位的錯誤 |
| 401 | 未登入、token 無效,或參與者身分核對失敗、改票憑證無效 |
| 403 | 不是活動擁有者;AI 額度用完 |
| 404 | 活動或留言不存在 |
| 409 | 狀態衝突:活動已定案或已取消、投票已截止、AI 請求進行中 |
| 410 | 連結已失效(活動結束超過 7 天) |
| 429 | 留言太頻繁 |
| 502 / 503 / 504 | 上游失敗 / 服務未設定 / 上游逾時 |
| 500 | 未預期的錯誤,只回固定訊息,不洩漏內部細節 |

**錯誤一定留下紀錄。**

- 401、403(可能是憑證被冒用或竄改)記 warning;所有 5xx 記 error 並附上完整 traceback。log 內容包含請求方法、路徑、使用者 id、狀態碼與錯誤代碼。
- AI 推薦的每一種結果(成功、失敗、額度不足、進行中被擋)都會輸出結構化 JSON log,包含延遲、token 用量、費用,方便在 Loki 依欄位查詢。

## 4.5 降級策略(fail-open 與旁路)

| 功能 | 故障時怎麼降級 | 為什麼這樣選 |
| --- | --- | --- |
| 留言限流 | 視同搶到鎖,照常寫入留言 | 限流是附加保護,不應該因為 Redis 故障讓留言功能整個不能用 |
| 通知信 | API 成功、信沒寄出,記 log | 定案已經成功,不能因為寄信失敗讓使用者以為定案失敗而重複操作 |
| AI 推薦 | 服務未設定時回 503,並讓額度 API 回 `serviceAvailable: false` | 前端可以先停用按鈕,不讓使用者白等 |
| 可觀測性 | Alloy 不在任何服務的依賴中;部署時缺少觀測設定只印警告 | 觀測系統的故障不應該影響產品,也不應該擋住部署 |
| `/metrics` | `METRICS_TOKEN` 沒設定時一律回 404(fail-closed) | 這是安全邊界,寧可收不到 metrics,也不能把 metrics 公開 |

## 4.6 資料一致性

這是本系統容錯設計的重點,分三層。

**第一層:用資料庫保證狀態只轉換一次(條件式 UPDATE)**

「先讀出狀態、檢查,再寫回」在併發時會出錯:兩個請求可能同時讀到「進行中」,然後都寫入成功。所以所有狀態轉換都改成**在 UPDATE 的 WHERE 條件裡檢查**,再看實際更新了幾列:

```python
affected = Event.objects.filter(pk=event.id, status="active").update(status="finalized", ...)
if affected == 0:
    # 有人先一步改過了,回 409
```

資料庫保證同一列同時只會有一個 UPDATE 成功。用到這個做法的地方:

- 定案、取消、重新開放活動
- 改票憑證的一次性消費(同時檢查「未使用」與「未過期」)
- 刪除留言(已刪除的不能再刪一次)
- AI 推薦紀錄從 pending 轉成 succeeded 或 failed

**第二層:需要「先檢查再寫入」時,用列鎖排隊(`SELECT ... FOR UPDATE`)**

有些情況無法只靠一個 UPDATE 完成,例如「本月已用次數未達上限才建立新紀錄」。這時先鎖住相關的列,讓同時進來的請求排隊:

- **AI 額度預留**:鎖住該使用者的 `User` 列,在鎖內計算已用次數、建立 pending 紀錄。用使用者列而不是紀錄表,是因為額度為 0 筆時紀錄表沒有任何列可以鎖。
- **AI 確認時再檢查一次**:先鎖紀錄、再鎖使用者。這個順序和「刪除使用者時的連帶刪除」一致,避免兩邊互相等待造成 deadlock(這個問題由 code-review 發現並以測試重現後修正)。
- **選定餐廳**:鎖活動列(`FOR NO KEY UPDATE`),兩個分頁同時選不同餐廳時會依序寫入,也不會和取消、重新開放互相干擾。

**第三層:多筆寫入包在同一個 transaction 裡**

- 取消活動時,「活動狀態改為取消」和「所有投票軟刪除」在同一個 transaction 裡,要嘛都成功、要嘛都不生效。
- 改票時,「消費憑證」、「刪除舊的表態」、「寫入新的表態」在同一個 transaction 裡。
- 寄信排在 `transaction.on_commit` 之後,只有資料真的存進去才會寄。

**冪等性(重複送出會怎樣)**

| 操作 | 重複送出的結果 |
| --- | --- |
| 定案 / 取消 / 重新開放 | 第二次回 409,資料不變 |
| 改票 | 憑證已被使用,第二次回 401 |
| 選定同一間餐廳 | 回 200,紀錄與 `updatedAt` 都不變 |
| 刪除留言 | 第二次回 404 |
| 部署腳本 | 可以安全重跑,沒有變動的服務不會重啟 |
| 通知信 task | 執行時重新核對活動狀態與時間戳,已被後續操作蓋過的舊 task 不寄信(例如定案→重開→定案,不會寄兩次定案信) |
| 建立活動、首次投票、留言、AI 推薦 | **不是冪等的**:網路斷線後使用者重送,可能會重複建立。首次投票有「同活動暱稱不可重複」擋住;AI 推薦有「同活動同時只能一個請求」;建立活動與留言沒有伺服器端的冪等鍵 |

## 4.7 已知缺口

以下缺口的處理方式與優先順序記錄在第 6 章:

- **資料庫沒有備份。** Postgres 資料只存在 EC2 根磁碟上的 Docker volume。
- **單機,沒有高可用。** EC2 故障或部署期間,服務會中斷。
- **通知信沒有重試,SMTP 也沒有設定逾時。** 寄信失敗不會補寄;SMTP 卡住時,`concurrency=1` 的 worker 會停在那封信,後面的信都要等。
- **部署時先啟動新版本,才執行 migrate。** 新程式碼可能在資料表還沒更新前就開始接請求。
- **告警尚未建立。** Dashboard 已經有了,但出問題時還不會主動通知(task 4.2)。
