## Why

System 與 User prompt 皆要求 3 到 5 間，且只有不足 3 間才允許擴大地理範圍，導致回傳 3 間就符合要求。產品希望優先提供 5 個餐廳選項。

## What Changes

- 兩個 prompt 同步以 5 間不同餐廳為目標；不足 5 間時繼續搜尋鄰近區域。
- 搜尋後仍不足 5 間，接受有搜尋依據的較少結果，並要求說明原因，不編造或重複湊數。
- notes 可記載實際範圍調整、數量不足及具體未確認資訊，消除原規則 1 與規則 6 的矛盾。
- 未查到菜單、營業狀態或容量時須明確標記未知，不要求推測；不為湊數忽略忌口／過敏條件。
- API schema、後端最多 5 間的處理、模型設定與搜尋工具保持既有行為；不新增額外 API 請求。

## Scenarios

- 原範圍已有 5 間有依據的餐廳：推薦 5 間，沒有其他補充事項時 notes 為 null。
- 原範圍只有 3 或 4 間：繼續搜尋鄰近區域，實際擴大範圍須於 notes 說明。
- 繼續搜尋仍不足 5 間：回傳可用結果並說明不足原因，不用重複或虛構店家補齊。
- 無法確認菜單、容量或營業狀態：明確標記未知，查不到的 nullable 欄位填 null。
